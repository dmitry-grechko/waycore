## Migration Checklist Per App

For each app, complete these steps:

### 1. Create Directory Structure
```bash
mkdir -p device/apps/{app}/qml
mkdir -p device/apps/{app}/backend  # if has backend
```

### 2. Create Manifest
```json
{
  "id": "com.waycore.{app}",
  "name": "{AppName}",
  "version": "1.0.0",
  "icon": "{emoji}",
  "category": "{category}",
  "entry": {
    "qml": "qml/{App}Main.qml",
    "backend": "backend/service.py"  // optional
  },
  "tier": 1 or 2,
  "enabled": true
}
```

### 3. Migrate QML Files
- Copy QML files to new location
- Update imports:
  - `import "." as App` → `import "../../core/qml" as Core`
  - `import "components" as UI` → `import "../../core/qml/components" as UI`
- Update Theme references: `App.Theme.` → `Core.Theme.`
- Add `closeRequested` signal for back navigation

### 4. Migrate Backend (if applicable)
- Move bridge code to `backend/service.py`
- Add `create_bridge()` factory function
- Update imports for new location

### 5. Update AppShell
- Remove old Component definitions
- Add dynamic loading via AppBridge

### 6. Test
- App appears in home grid
- App launches successfully
- All features work
- Back navigation works

## Open Questions

### Container Strategy for Apps (Research Required)

**Question**: Should each app run in its own Docker container, or should there be a centralized container that manages all apps?

#### Option A: One Container Per App
**Pros:**
- Strong isolation between apps (security, stability)
- Independent scaling and resource limits
- Apps can crash without affecting others
- Clear deployment/update boundaries
- Third-party apps can't access other app's data

**Cons:**
- Higher resource overhead (memory per container)
- More complex orchestration
- Inter-app communication requires networking
- Slower app startup (container init)
- More complex development workflow

#### Option B: Centralized App Manager Container
**Pros:**
- Lower resource footprint
- Simpler orchestration
- Faster app switching (no container startup)
- Easier shared state management
- Simpler development/debugging

**Cons:**
- One app crash can affect others
- Weaker isolation for third-party apps
- Harder to enforce resource limits per app
- Security boundaries less clear

#### Option C: Hybrid Approach
- Core/built-in apps run in centralized container
- Third-party/untrusted apps run in isolated containers
- Evaluate based on app tier/trust level

**Considerations:**
- Device resource constraints (embedded/portable device)
- Third-party app ecosystem requirements (Phase 18.7+)
- Security requirements for untrusted code
- Impact on startup time and UX
- Development complexity

**Action**: Research and document recommendation before implementing third-party app support (18.7+).
